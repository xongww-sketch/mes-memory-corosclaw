## 重新读基线，三个硬事实

**① Tab2 的 33 个节点里，只有 17 个是活的**

从 Webhook 走连线，16 个节点根本不可达——`划分时间区间1`、`Code2`、`Respond to Webhook1` 这一整套是废弃副本。Tab5 更极端：**13 个节点只有 5 个生效**。

改造只需动生效链路。**但如果直接在原工作流上改，很容易改到死链上去，白干还查不出问题。**

**② Tab2 慢的真正原因，比"逐月切片"更严重——是笛卡尔式膨胀**

```js
// 划分时间区间：N个月 → 每个机型一条记录
// 构建查询数据：flatMap → 机型 × 月份 全展开
```

每个「机型×月份」组合都是一个独立 item，每个 item 各查 1 次激活 + 1 次不良。

B18 查 2020/08–2026/06 = **71 个月 × 2 = 142 次数据库往返**。会议说的 5 组多选一叠 → **710 次**。这就是需求 7 说的"查不出来"。

**③ Tab5 的 SQL 里藏着一个会吃掉数据的过滤条件**

```sql
AND dr.defective_duration_days >= 0
```

失效时点是用 `激活时间 + defective_duration_days` 反算的，不是读 `defective_date`。**只要 `duration_days` 是负数，这台设备就被完全排除在统计外。**

这条我上一轮验过（负值有 3843 条，占 6.75%），但按你的要求，**旧结论一律作废，我会重新跑 SQL 验一遍再下结论**。
