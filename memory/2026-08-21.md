### 唯一需要做的动作

只跑一条 UPDATE 补 production_detail，工作流不用改：

```sql
UPDATE mes_daily_data.production_detail pd
SET wifi_mac = m.mac
FROM (
  SELECT DISTINCT ON (r.retroid) r.retroid, md.data->>'mac' AS mac
  FROM mes.machine_data md
  JOIN mes.retroid r ON r.retroid_id = md.retroid_id
  WHERE md.procedure_detail_id IN (148, 42)
    AND md.data->>'mac' IS NOT NULL AND length(md.data->>'mac') = 12
  ORDER BY r.retroid, md.machine_data_id DESC
) m
WHERE pd.retroid = m.retroid AND (pd.wifi_mac IS NULL OR pd.wifi_mac = '');
```

补了快照层，后续出库自然抄到正确值。

## 🔧 顺带交付：selectBind_api 慢查询诊断（8/20）

工作流 `jymdJtzSFJ9wMS9c`，接口 3.5s。

**根因：`md.data ->> 'material' = '...'` 在 JSONB 上无函数索引，全表扫 `mes.machine_data`。**

决定性证据（交替压测 10 轮稳定复现）：
- `PPW3500402` → 3.5~4.9s
- `PPW3500478` → 0.16~0.41s
- 不存在的物料 `ZZZZNOTEXIST999` → 0.10s（排除"数据量大"）

慢跟着**物料值**走，不跟 SN、不跟并发。原因是 `ORDER BY createtime DESC LIMIT 1` 让 PG 倒序扫索引，命中行在时间轴靠前就要扫几百万行。

对照组 `selectBlind_api_temp`（14 节点，无辅料链）0.15s，差 23 倍。

更慢的兄弟：`bind_id_query_material` 9.3~12.1s，`bind_id_query_material_for_appsmith_table` 9.6s（用了 `= ANY(string_to_array(data->>'bind_id',';'))`，三重叠加）。

**修法**：
```sql
CREATE INDEX CONCURRENTLY idx_machine_data_material ON mes.machine_data ((data ->> 'material'));
CREATE INDEX CONCURRENTLY idx_machine_data_bind_id ON mes.machine_data ((data ->> 'bind_id'));
CREATE INDEX CONCURRENTLY idx_machine_data_material_createtime ON mes.machine_data ((data ->> 'material'), createtime DESC);
```
必须带 CONCURRENTLY，停产时段执行。

报告：`reports/selectBind_api_慢查询诊断_20260820.md`

## daily_info 结构性问题（长期）
